# Лабораторна робота №4

**Тема:** інтеграція із зовнішніми Web API та автоматизоване тестування Python-коду.
Мета — отримувати відомості про вразливості через NVD CVE API 2.0, перевіряти
зовнішні дані, відокремлювати аналіз від введення/виведення та тестувати
звичайні, граничні й помилкові сценарії без інтернету.

Студент: Перестюк Назарій Романович, група КБ-205. **Варіант №2** імпортується
з `shared.student.VARIANT_NUMBER`; інші студентські дані не змінювалися.

## Правило варіанта №2

```python
score >= 8.0 and attackComplexity == "LOW"
```

`attackComplexity` описує складність умов, потрібних для успішної атаки.
Допустимі значення CVSS v3.1 — `LOW` та `HIGH`. Правило дає `review` лише
за одночасного виконання обох умов; оцінка **8.0 включається**.

Розглядається виключно `metrics.cvssMetricV31`. Вибирається перший `Primary`,
а за його відсутності — перший елемент. Число, ознака, джерело й вектор
беруться з одного вибраного запису. Інші оцінки після вибору не аналізуються;
усі елементи списку повинні бути об'єктами. CVSS v2/v4 не підставляються,
перерахунку за вектором немає.

Таблиця правил у коді охоплює номери 1–15 для дотримання загального контракту
методички. Поточний запуск завжди використовує номер **2** зі спільного модуля;
CLI-аргументу для зміни варіанта немає. `bool`, нецілі числа та номери поза
1–15 відхиляються до читання даних або запиту.

## Локальний режим

```bash
python -m labs.lab04.main --cve CVE-2099-10001 --input labs/lab04/data/nvd_sample.json
```

`--cve` обов'язковий навіть із файлом. Повний регістрозалежний шаблон:
`CVE-[0-9]{4}-[0-9]{4,}`. Перевірка шаблону не встановлює існування CVE.
`--input` приймає шлях до UTF-8 JSON. У цьому режимі HTTP-запитів немає,
а `vulnerabilities[0].cve.id` має точно збігатися з аргументом.

Приклад містить **вигаданий** `CVE-2099-10001`; використовуйте його тільки
локально. Файл скопійовано без зміни вмісту.

Фактично отриманий повний звіт, код завершення **0**, stderr порожній:

```json
{
  "cve_id": "CVE-2099-10001",
  "variant": 2,
  "description": "Synthetic vulnerability for offline API testing.",
  "vuln_status": "Analyzed",
  "cvss_version": "3.1",
  "score": 9.8,
  "score_source": "nvd@nist.gov",
  "vector": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H",
  "rule": {
    "threshold": 8.0,
    "field": "attackComplexity",
    "expected": "LOW"
  },
  "observed": "LOW",
  "decision": "review"
}
```

На успішному запуску stdout містить лише один JSON-об'єкт із
`ensure_ascii=False`. Усі ключі цього формату присутні завжди, відсутні дані
позначаються `null`; порядок ключів і відступи не є частиною контракту.

## Стани decision і перевірка даних

Стани перевіряються за таким пріоритетом:

| Стан | Умова |
| --- | --- |
| `not_found` | Коректний порожній список `vulnerabilities` |
| `rejected` | Статус точно `Rejected`; CVSS не аналізується |
| `insufficient_data` | Статус, CVSS v3.1 або поле правила відсутні |
| `review` | Оцінка не нижча за 8.0 та `attackComplexity == "LOW"` |
| `other` | Даних достатньо, але обидві умови одночасно не виконано |

Для `not_found` дані запису — `null`, а `cve_id`, `variant` і `rule` заповнені.
Для `Rejected` чи відсутнього статусу зберігаються доступні статус і опис;
усі поля оцінки та `observed` — `null`, навіть якщо `metrics` некоректний.
Якщо бракує лише `attackComplexity`, доступні поля вибраної оцінки зберігаються.

Верхній рівень — об'єкт із `vulnerabilities`, списком 0–1 елементів.
Наявний статус повинен бути непорожнім рядком. Усі записи необов'язкового
списку `descriptions` перевіряються на рядкові `lang` і `value`; вибирається
перший непорожній опис із `lang == "en"`.

Відсутні `metrics`, `cvssMetricV31` чи порожній список — брак оцінки.
Наявні `null` або неправильні типи — помилка структури. Вибрана оцінка
повинна містити об'єкт `cvssData` з числовим, скінченним `baseScore` у межах
0–10; `bool`, рядки, NaN та нескінченність не допускаються. Необов'язкові
`version`, `vectorString`, `source` за наявності — непорожні рядки;
`version` має дорівнювати `"3.1"`. Відсутнє поле варіанта — брак даних,
наявне некоректне значення — помилка.

Внутрішній запис описано в docstring `extract_record`: нормалізовані поля
звіту та незалежна глибока копія одного `cvssData`. Поле індивідуального
правила перевіряє `build_report`. Порушення структури спричиняють
`DataValidationError`, підклас `ValueError`. Аналіз не змінює payload,
не читає файлів, оточення чи часу, не друкує та не звертається до мережі.

`insufficient_data` **не означає відсутності небезпеки**: даних недостатньо
для цього правила. `other` також не підтверджує безпечності. `review` означає
відповідність навчальній умові, а не готовий пріоритет усунення. CVSS описує
технічну серйозність, а не ризик конкретної організації.

## Режим NVD API

```bash
python -m labs.lab04.main --cve CVE-2021-44228
```

Виконується один GET до `https://services.nvd.nist.gov/rest/json/cves/2.0`
із `params={"cveId": cve_id}`, `timeout=(3.05, 10)`,
`allow_redirects=False` і стандартною ввімкненою перевіркою TLS.
Викликається `raise_for_status()`, додатково вимагається статус 200,
після цього викликається `response.json()`.

Завжди передається `Accept: application/json`. Ключ необов'язковий:
`build_headers()` читає `NVD_API_KEY` через `os.getenv()` під час кожного
виклику. Крайні пробіли обрізаються, порожній ключ не передається.
Непорожній ключ передається лише в заголовку `apiKey`, без Bearer і URL.
Справжній ключ у файлах проєкту не потрібний. За потреби встановіть його
через захищене середовище запуску; тести використовують лише вигадані значення.

Перед ручним запуском ознайомтеся з [правилами NVD](https://nvd.nist.gov/developers/start-here)
і [умовами використання](https://nvd.nist.gov/developers/terms-of-use).
Дотримуйтеся актуальних лімітів сервісу. Для розроблення й демонстрації
використовуйте локальний файл; не запускайте масове завантаження чи циклічне
опитування. У програмі немає автоматичних повторів або переходів за посиланнями.
Цей навчальний інструмент використовує дані API NVD; він не схвалений
і не сертифікований NVD.

**Фактична перевірка 15.11.2026:** після локальних тестів виконано один ручний
запит за наведеною командою з дозволеним мережевим доступом. Отримано
HTTP **503**, код завершення **1**, stdout порожній, stderr:

```text
Помилка: Неочікуваний HTTP-статус NVD: 503.
```

Успішне отримання живого запису в цьому середовищі не підтверджено.
Автоматичних повторів не виконувалося. Попередня спроба в ізольованому
середовищі завершилася помилкою з'єднання. Автоматичне отримання сторінки
правил NVD повернуло HTTP 403, тому актуальні числові ліміти тут не фіксуються.

## Помилки та коди завершення

| Код | Значення |
| --- | --- |
| `0` | Сформовано звіт, включно з `not_found`, `rejected`, `insufficient_data`, `other` |
| `1` | Помилка HTTP, мережі, JSON, читання UTF-8 файла або структури даних |
| `2` | Неправильні аргументи чи номер варіанта |

Помилки спрямовуються лише у stderr без traceback, текстів мережевих
винятків, тіл помилкових відповідей, ключів чи заголовків із секретами.
`ConnectionError`, `Timeout`, `HTTPError`, неочікувані статуси, неправильний
JSON, `OSError`, неправильне кодування й порушення структури мають окремі
повідомлення. HTTP 404 є помилкою отримання, а не станом `not_found`.
Помилки аргументів використовують стандартний механізм `SystemExit(2)` argparse.

Приклад помилкового запуску для захисту, очікується код 2:

```bash
python -m labs.lab04.main --cve cve-2099-10001 --input labs/lab04/data/nvd_sample.json
echo $?
```

## Автоматизовані перевірки

```bash
python -m pytest labs/lab04/tests -q
ruff check labs/lab04
ruff format --check labs/lab04
```

Фактичний результат: **243 passed**; `ruff check` — **All checks passed!**;
`ruff format --check` — **10 files already formatted** (код і документація).
Окремої конфігурації Ruff у репозиторії немає, використано наявні стандартні
налаштування без вимкнення правил.

Автоматична фікстура перед кожним тестом видаляє успадкований `NVD_API_KEY`
і метод `requests.sessions.Session.request`. Тести клієнта підміняють лише
`api_client.requests.get` через `Mock`, тому перевіряють справжній код
клієнта. `deepcopy` ізолює структури, `tmp_path` — файли, `capsys` — stdout
і stderr. Тести не потребують і не виконують справжніх мережевих запитів.

Перевірено межі 7.9 / 8.0 / 8.1, значення LOW/HIGH, усі п'ять станів,
вибір першого Primary, fallback на першу оцінку, незмішування джерел,
помилки вкладених типів, необов'язкових полів і CVSS, незмінність даних,
заголовки, таймаути, HTTP-помилки й перенаправлення, локальний режим,
коди завершення, безпечність повідомлень та відсутність I/O при імпорті.
Уявна заміна `>=` на `>` порушить перевірку `8.0 + LOW → review`.
Зміни `baseScore` у тестах ізолюють порівняння, не перераховують CVSS вектора.

Для окремого успішного сценарію й перевірки обробки помилки:

```bash
python -m pytest labs/lab04/tests/test_analysis.py -k boundary -v
python -m pytest labs/lab04/tests/test_main.py -k local_failures -v
```
